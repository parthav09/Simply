# Simply synthetic fine-tuning demo

Use **JSONL for training**. Each line is one complete JSON object with a
`messages` array: the exact Simply shopper prompt followed by the desired
assistant response. The response is a string containing one JSON action.
CSV is useful for catalog tables, but nested observations and conversation
messages are easier to preserve correctly in JSONL.

This is a small, artificially generated **pipeline demo**, not a production
training corpus, human behavior dataset, or evidence of model performance.
No model calls, paid requests, or changes to the live agent were made.

## Files

- `train.jsonl`: training examples.
- `validation.jsonl`: demonstration validation examples for development.
- `test.jsonl`: demonstration test examples; keep separate from training and tuning.
- `preview.json`: readable excerpts with targets; **do not train on these shortened observations**.
- `provenance.jsonl`: synthetic source, mission group, layout, fixture event and hashes for every example; kept out of model input.
- `manifest.json`: actual counts, action coverage, limitations and checksums.
- `fixtures/`: twelve explicitly labeled offline canonical recordings for audit.
- `generate_demo.py`: reproducible generator using the current Python engine.
- `verify_demo.py`: read-only checks of files, labels, provenance and canonical transitions.

## What one example looks like

Abbreviated for explanation only; the training files contain full prompts:

```json
{
  "messages": [
    {"role": "user", "content": "[Full Simply profile, shopping mission, floor map, cart, current observation and allowed actions]"},
    {"role": "assistant", "content": "{\"step\":\"grab\",\"product_id\":\"P0001\",\"reason\":\"Collect the requested bananas.\"}"}
  ]
}
```

The outer object is the training example. The assistant's `content` remains
text because language models generate text. That text must parse into Simply's
`step`, `product_id`, `reason` action object. Empty `product_id` is used for
movement and checkout. There is one proposal per action.

The dataset intentionally uses the existing user-only runtime prompt, without
introducing a separate system prompt that the deployed agent would not receive.

## How these examples were generated

Six synthetic missions each run in Layout A and Layout B, with two unique
requested products per shopper. Each recording is a **one-shopper offline
fixture**, an explicit exception to the ordinary 10–15 shopper model-run scope.
Mission 3 starts inside the store to include leftward movement. Other missions
start at the usual spawn. Profile templates and product facts come from the
repository CSV files; names, missions and selected preferences are synthetic.

A deterministic offline teacher reads only the prompt and proposes a route,
requested pickup or checkout. The real `SimulationSession` applies every action
through Python core and records it. `read_run` validates each full recording.
The teacher is labeled `scripted_test` and never registered as a live provider.
No historical model recordings were modified or included.

Labels imitate a narrow map-based shopping-list collector, **not Luna, Terra,
Qwen, or an empirically validated human shopper**. No navigation adjustment is
mixed into the labels: recordings use `model_only` execution with an explicit
offline rule teacher. The word `model_only` names the engine's no-assistance
policy; it does not mean these recordings were generated by a model.

The labels demonstrate legal moves, shelf pickups, no duplicate products,
payment in one checkout action, and some deliberate valid overspending.
The teacher does not model impulse purchases, removals, mistake recovery,
realistic budget sensitivity or calibrated persona differences. Movement is
overrepresented. Do not treat every legal action as a behaviorally optimal label.

Mission groups 1–4 train, group 5 validates, and group 6 tests. Both layouts of
each mission stay together. Splitting individual steps randomly would leak
near-identical trip states between training and evaluation. The splits share
the catalog and layouts, and profile templates come from the existing project;
these tiny splits do not establish independent generalization or human realism.

## Load for supervised fine-tuning

Hugging Face Datasets can load these files directly:

```python
from datasets import load_dataset

dataset = load_dataset("json", data_files={
    "train": "data/finetuning_demo/train.jsonl",
    "validation": "data/finetuning_demo/validation.jsonl",
    "test": "data/finetuning_demo/test.jsonl",
})
print(dataset["train"][0]["messages"])
```

Use the selected Qwen checkpoint's own tokenizer/chat template. For Qwen3,
keep non-thinking configuration consistent between training and inference;
the desired runtime response here is just the final action JSON. Configure
loss on assistant output and verify the trainer/template supports its masking
correctly. Do not unintentionally train the model to reproduce the large user
prompt. Inspect tokenized examples and ensure truncation never removes the
current observation or assistant target. This bundle prepares data; it does
not install a training stack or fine-tune a model.

References:

- [TRL conversational dataset formats](https://huggingface.co/docs/trl/dataset_formats)
- [TRL SFT trainer and assistant-only loss](https://huggingface.co/docs/trl/sft_trainer)
- [Qwen3-8B chat template and non-thinking mode](https://huggingface.co/Qwen/Qwen3-8B)

## Verify or regenerate

From the repository root:

```bash
.venv/bin/python data/finetuning_demo/verify_demo.py
.venv/bin/python data/finetuning_demo/generate_demo.py --output /tmp/simply-qwen-demo-new
```

Generation refuses to replace existing generated files. Core and catalog
changes can change future examples. Run IDs, timestamps and timing fields in
audit fixtures vary between generations; with the same source inputs and
generator, the training pairs are deterministic.

## Before a real fine-tune

1. Evaluate the untouched Qwen checkpoint on genuinely held-out Simply tasks.
2. Expand beyond this rule teacher: collect and review task-specific model or human demonstrations, preserving original proposal versus applied-action provenance.
3. Add preference-sensitive decisions, rejected-action recovery and less repetitive routes. Preserve soft budgets and the current shopping rules.
4. Reserve independent shopper/mission groups before generating training data. Include unseen arrangements or product mixes when testing those kinds of generalization.
5. Train a small pilot, inspect failures, then expand. Thousands of repeated route steps do not substitute for diverse, correct decisions.
6. Compare tuned and untuned Qwen with the same prompts, assistance policy and action limits. Report completion, fulfillment, invalid actions, loops, assistance rate, latency and compute costs.

Synthetic examples are useful because the engine can validate physical
correctness cheaply. They cannot by themselves establish human realism,
layout uplift or retail impact. Keep this bundle outside live history and
public evidence; do not export its fixtures as a model showcase.
